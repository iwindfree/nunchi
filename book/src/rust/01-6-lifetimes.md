# 1.6 수명 표기가 왜 여섯 번뿐인가

> **선행 장**: [1.3 빌림 `&`와 `&mut`](01-3-borrow.md), [1.5 문자열 세 종류](01-5-strings.md)
> **연습문제**: 2개

수명 표기(`<'a>`)는 Rust를 배우다 그만두는 가장 큰 이유로 꼽힙니다. 그런데
nunchi 코드 7,788줄에 **여섯 번**밖에 나오지 않습니다. 이 장은 왜 그런지
설명하고, 나올 때 무슨 뜻인지 알려 드립니다.

## 수명이 무엇을 막는가

빌린 것이 원본보다 오래 남아 있으면 오류가 납니다.

```rust
fn broken() -> &String {
    let s = String::from("hello");
    &s                      // s 는 함수가 끝나면 사라집니다
}                           // 그런데 그것을 가리키는 참조를 돌려줍니다
```

이 코드는 컴파일되지 않습니다. 돌려준 참조가 이미 사라진 메모리를 가리키기
때문입니다. C++에서 이것이 실제로 자주 발생하던 오류이며, Rust는 컴파일 시점에
막습니다.

컴파일러가 이것을 판단하려면 **각 참조가 얼마나 오래 살아 있는지** 알아야
합니다. 그 정보를 수명(lifetime)이라고 부릅니다.

## 대부분은 적지 않아도 됩니다

핵심은 여기입니다. **수명은 항상 존재하지만 대부분 컴파일러가 알아서
계산합니다.** 적어야 하는 경우는 컴파일러가 판단할 수 없을 때뿐입니다.

```rust
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}
```

참조를 받아 참조를 돌려주는데도 표기가 없습니다. 컴파일러가 이렇게 추론하기
때문입니다. **입력이 참조 하나뿐이면 출력은 그것에서 온 것이다.**

이 추론 규칙을 수명 생략 규칙(lifetime elision)이라고 부릅니다. 실제 코드의
대부분이 이 규칙에 들어맞습니다.

## 적어야 하는 경우

컴파일러가 판단할 수 없는 상황이 두 가지입니다.

**첫째, 참조를 여러 개 받고 그중 하나를 돌려줄 때입니다.**

```rust
fn longer(a: &str, b: &str) -> &str {    // 오류입니다
    if a.len() > b.len() { a } else { b }
}
```

돌려주는 것이 `a`에서 온 것인지 `b`에서 온 것인지 컴파일러가 모릅니다.
그래서 직접 알려 줘야 합니다.

```rust
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}
```

`<'a>`는 이름표입니다. "`a`와 `b`와 반환값이 모두 같은 수명을 갖는다"고
알려 주는 것입니다. 즉 **셋 중 가장 짧게 사는 것만큼만 살아 있다**고 봅니다.

**둘째, 구조체가 참조를 필드로 가질 때입니다.**

```rust
struct Holder<'a> {
    text: &'a str,
}
```

이 구조체는 자기가 가리키는 문자열보다 오래 살 수 없습니다. 그 제약을 타입에
적어 두는 것입니다.

## nunchi가 수명을 거의 안 쓰는 이유

**구조체가 참조를 갖지 않기 때문입니다.**

```rust
// crates/nunchi-core/src/model.rs 에서
pub struct Node {
    pub id: NodeId,
    pub name: String,          // &str 이 아니라 String 입니다
    pub repo: String,
    pub path: Option<String>,
    // ...
}
```

모든 필드가 소유한 값입니다. 그래서 수명 표기가 필요 없습니다.

이것이 [1.4장](01-4-clone.md)에서 본 `clone` 170개와 직접 연결됩니다.
**소유하는 구조체를 쓰기로 한 대가가 복사이고, 얻는 것이 수명 표기 없는
코드입니다.**

만약 `Node`가 참조를 갖게 설계했다면 이렇게 됐을 것입니다.

```rust
pub struct Node<'a> {
    pub name: &'a str,
    pub repo: &'a str,
    // ...
}
```

그러면 `Node`를 담는 모든 것에 수명이 따라붙습니다.

```rust
fn upsert_nodes<'a>(&mut self, nodes: &[Node<'a>]) -> Result<usize>
fn build_pack<'a>(...) -> Vec<Node<'a>>
```

그리고 함수 안에서 만든 `Node`를 밖으로 돌려줄 수 없게 됩니다. 원본 문자열이
함수 안에 있기 때문입니다.

**복사 비용과 코드 복잡도를 맞바꾼 것이며, 이 프로젝트에서는 그 선택이
맞았습니다.** `NodeId` 복사는 수십 바이트인데, 수명 표기가 코드 전체에
퍼지면 읽기가 훨씬 어려워집니다.

## 실제로 나오는 여섯 번

수명 표기가 나오는 두 파일을 봅니다.

```rust
// crates/nunchi-core/src/framework.rs 에서
fn text<'a>(node: Node, src: &'a [u8]) -> &'a str {
    node.utf8_text(src).unwrap_or_default()
}
```

참조를 두 개 받습니다. `node`는 tree-sitter의 노드이고 `src`는 원본 바이트
배열입니다. 돌려주는 문자열은 **`src`에서 온 것**입니다. `node`가 아닙니다.

컴파일러는 그 사실을 모르므로 알려 줘야 합니다. `src: &'a [u8]`와
`-> &'a str`에 같은 이름표를 붙여서 "반환값은 `src`만큼 산다"고 알립니다.

```rust
fn annotations_of<'a>(decl: Node<'a>, src: &'a [u8]) -> Vec<(String, Option<String>)> {
```

여기도 같은 이유입니다. tree-sitter의 `Node`가 원본 바이트를 가리키고 있으므로
둘의 수명을 묶어야 합니다.

**여섯 번 모두 tree-sitter 때문입니다.** 외부 라이브러리가 참조를 쓰는 구조라
어쩔 수 없이 따라간 것이고, nunchi가 직접 설계한 타입에는 하나도 없습니다.

## 읽는 법 요약

| 표기 | 읽는 법 |
|---|---|
| `&str` | 빌린 문자열입니다. 수명은 컴파일러가 계산합니다 |
| `&'a str` | 빌린 문자열이며 수명 이름표가 `'a`입니다 |
| `fn f<'a>(...)` | 이 함수에서 쓸 수명 이름표를 `'a`로 선언합니다 |
| `struct S<'a>` | 이 구조체는 `'a`만큼 사는 참조를 갖습니다 |
| `&'static str` | 프로그램이 끝날 때까지 삽니다. 코드에 직접 쓴 문자열이 이렇습니다 |

`'a`라는 이름 자체에는 의미가 없습니다. `'b`나 `'src`로 써도 됩니다. 같은
이름끼리 묶인다는 사실만 중요합니다.

## 연습문제

### 문제 1 [읽기]

아래 함수에 수명 표기가 필요합니까?

```rust
// (가)
fn trim_prefix(s: &str) -> &str {
    s.strip_prefix("file:").unwrap_or(s)
}

// (나)
fn pick(a: &str, b: &str, use_first: bool) -> &str {
    if use_first { a } else { b }
}

// (다)
fn count(s: &str) -> usize {
    s.len()
}
```

(나)에만 필요합니다.

(가)는 참조를 하나만 받으므로 컴파일러가 "반환값은 `s`에서 왔다"고 추론합니다.

(나)는 참조를 두 개 받고 그중 하나를 돌려주므로 어느 쪽인지 알려 줘야 합니다.

```rust
fn pick<'a>(a: &'a str, b: &'a str, use_first: bool) -> &'a str
```

(다)는 참조를 돌려주지 않고 숫자를 돌려주므로 수명과 무관합니다.

## 정리

수명은 빌린 것이 원본보다 오래 사는 상황을 막습니다. 항상 존재하지만 대부분
컴파일러가 계산하므로 적지 않아도 됩니다.

적어야 하는 경우는 참조를 여러 개 받아 하나를 돌려줄 때와, 구조체가 참조를
필드로 가질 때입니다.

nunchi에 수명 표기가 여섯 번뿐인 이유는 **모든 구조체가 값을 소유하기
때문입니다.** 그 대가로 `clone`이 늘었지만 코드는 훨씬 읽기 쉬워졌습니다.
여섯 번은 모두 tree-sitter 때문이며 직접 설계한 타입에는 없습니다.
