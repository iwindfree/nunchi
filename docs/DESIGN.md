# 설계 문서

이 문서는 두 가지 질문에 답합니다. 첫째, nunchi가 어떤 방식으로 토큰을
줄이는지 설명합니다. 둘째, 여러 대안 가운데 지금의 구조를 선택한 근거를
밝히고, 그 결정을 뒤집어야 하는 조건까지 함께 적어 둡니다.

---

## 1. 해결하려는 문제

에이전트가 코드베이스에서 무언가를 고치려면 먼저 구조를 파악해야 합니다.
지금 방식에서는 매번 처음부터 다시 파악합니다.

```
1. Grep "retry"                    →  40건 일치
2. Read OrderService.java 등       →  18k 토큰
3. Grep "payment"                  →  60건 일치
4. Read 파일 4개                   →  22k 토큰
   (반복)
   12턴 · 입력 약 60k 토큰 · 프런트엔드 쪽 영향은 끝까지 파악하지 못함
```

같은 코드베이스에서 세션마다 이 작업이 되풀이됩니다. 구조는 변하지 않았는데도
매번 다시 발견하고 있습니다.

미리 계산해 둔 그래프가 있으면 같은 작업이 이렇게 바뀝니다.

```
1. nunchi_pack{task:"주문 재시도 로직 수정", budget:4000}   →  3.8k 토큰
2. Read OrderService.java:88-141  (팩이 지목한 범위만 읽습니다)  →  3k 토큰
3. Edit
   3턴 · 입력 약 9k 토큰 · 프런트엔드 훅에 미치는 영향까지 파악함
```

## 2. 핵심 원칙: 답이 아니라 좌표를 제공합니다

`nunchi_pack`이 돌려주는 것은 코드 덩어리가 아니라 순위가 매겨진 좌표 목록입니다.

```jsonc
"items": [
  { "tier": "L2", "ref": "api/.../OrderService.java:88-141",
    "sym": "findOne", "body": "..." },              // 전체 본문, 상위 두세 개만
  { "tier": "L1", "ref": "api/.../OrderController.java:44",
    "sym": "getOrder",
    "sig": "@GetMapping(\"/api/orders/{id}\") ..." }, // 시그니처와 문서
  { "tier": "L0", "ref": "api/.../OrderServiceTest.java:12",
    "sym": "findOne_retriesOnTimeout" }             // 좌표 한 줄
]
```

에이전트는 이 목록을 보고 실제로 필요한 범위만 읽습니다. 파일 12개를 통째로
읽으면 약 35k 토큰이 들지만, 심볼 40개를 이 방식으로 담으면 약 4k 토큰에
정확한 위치까지 함께 전달됩니다.

절감을 만드는 동작은 두 가지입니다.

1. **선별**: 노드 수천 개 가운데 관련된 수십 개만 고릅니다.
2. **강등**: 예산이 부족해지면 상세도를 L2에서 L1으로, 다시 L0으로 낮춥니다.

## 3. 그래프의 구성

노드는 18종이고 엣지는 19종입니다. 그중 중요한 것만 추리면 다음과 같습니다.

```
Repo ──contains──▶ File ──contains──▶ Symbol
                                        │
                    ┌───────────────────┼──────────────────┐
                    ▼                   ▼                  ▼
                  calls              injects            defined_in
              (다른 Symbol)        (Spring DI)            (File)

Route ──handles──▶ Symbol          ApiCall ──calls_api──▶ Route
(@GetMapping)      (컨트롤러 메서드)   (fetch, axios)

Entity ──persists_to──▶ Table       File ──co_changed_with──▶ File
(JPA, MyBatis, SQLAlchemy)          (git 이력에서 함께 바뀐 파일)
```

모든 엣지는 출처(`provenance`)와 신뢰도(`confidence`)를 속성으로 가집니다.
tree-sitter가 만든 추정 엣지와 빌드에 기반한 정밀 해소 결과를 구분하기
위해서입니다.

## 4. 프레임워크 의미론이 따로 필요한 이유

Spring에서는 호출 관계가 소스 코드에 구문으로 존재하지 않습니다.

| 실제 관계 | 소스에 보이는 것 |
|---|---|
| `GET /api/orders`에서 컨트롤러 메서드로 연결됨 | `@GetMapping` 어노테이션뿐임 |
| 서비스에서 구현체로 연결됨 | `@Autowired`와 인터페이스뿐임 |
| `findByStatus(...)` | 메서드 본문이 아예 없음 (JPA 파생 쿼리) |

tree-sitter로 호출 그래프만 뽑으면 호출 엣지가 거의 생기지 않습니다. 그러면
그래프가 사실상 파일 목록과 다르지 않게 됩니다.

실측이 이 사실을 확인해 주었습니다. RealWorld 저장소를 인덱싱했을 때 해소되지
않은 호출의 상위 항목은 `save`(45회, JPA 리포지터리라서 본문이 없습니다)와
`build`, `builder`(합계 85회, Lombok이 생성하는 코드입니다)였습니다.

그래서 어노테이션을 1급 대상으로 다룹니다.

- `@GetMapping("/{slug}")`와 클래스에 붙은 `@RequestMapping("/api/articles")`를
  합쳐서 `Route(GET, /api/articles/{})` 노드와 `HANDLES` 엣지를 만듭니다.
- `@Service`가 붙은 클래스의 `final` 필드에서 `INJECTS` 엣지를 만듭니다.
  Lombok의 `@RequiredArgsConstructor` 관용구를 처리하기 위해서입니다.
- `fetch(\`/api/articles/${slug}\`)`에서 `ApiCall` 노드를 만듭니다.

### 규칙을 코드가 아니라 데이터로 둡니다

`@GetMapping`을 Rust 코드에 직접 적어 두면, 새 프레임워크나 사내 관용구를
지원할 때마다 바이너리를 다시 빌드하고 다시 배포해야 합니다. 개발 장비와
업무 장비가 분리된 환경에서는 그 왕복 비용이 특히 큽니다.

프레임워크 의미론은 몇 가지 정형으로 환원됩니다. 그래서 규칙 표로 분리했습니다.

```toml
[[framework.route]]        # 메서드 어노테이션에서 라우트를 만듭니다
[[framework.base_path]]    # 클래스 어노테이션에서 경로 접두를 얻습니다
[[framework.bean]]         # 클래스 어노테이션으로 DI 등록 대상을 판별합니다
[[framework.inject]]       # 필드 어노테이션으로 주입 지점을 판별합니다
[[framework.http_client]]  # 지정한 인자가 URL임을 알려 줍니다
[[framework.persistence]]  # 엔티티, 테이블, SQL 매퍼를 판별합니다
```

Spring, NestJS, Micronaut, ASP.NET, Ktor, FastAPI, Flask가 모두 이 틀에
들어갑니다.

## 5. 교차 저장소 연결

grep으로는 원리적으로 얻을 수 없는 정보를 만드는 부분입니다.

```
  React                          Spring Boot                     DB
  useOrder.ts:31                 OrderController.java:44
  fetch(`/api/orders/${id}`) ──▶ @GetMapping("/api/orders/{id}")
        │        CALLS_API              │ HANDLES
        │                               ▼
        │                        OrderService.findOne
        │                               │ INJECTS
        │                               ▼
        │                        OrderRepository ──persists_to──▶ orders
```

경로 템플릿을 정규화하여 연결합니다.

| 표기 | 사용하는 곳 | 정규화 결과 |
|---|---|---|
| `/api/orders/{id}` | Spring | `/api/orders/{}` |
| `/api/orders/:id` | Express, react-router | `/api/orders/{}` |
| `` `/api/orders/${id}` `` | JavaScript 템플릿 리터럴 | `/api/orders/{}` |

세 표기가 같은 문자열로 바뀌므로 연결 판정은 단순 비교로 끝납니다.

그 결과 "주문 조회 API의 응답 필드를 바꾸면 무엇이 깨지는가"라는 질문에
프런트엔드 훅과 컴포넌트, 백엔드 서비스, 데이터베이스 테이블까지 한 번에
답할 수 있습니다.

### 분명히 밝혀 두어야 하는 두 가지

**첫째, 라우트를 정의하는 코드는 호출이 아닙니다.** miragejs의
`this.post('/users', handler)`나 Express의 `app.get('/x', h)`는 서버가 라우트를
등록하는 코드이며 클라이언트 호출이 아닙니다. 초기 구현에서 이 오탐이 탐지
21건 가운데 16건을 차지했습니다. 목 서버가 같은 API 명세를 그대로 반영하고
있었기 때문에 백엔드와 잘 연결되었고, 그래서 지표가 95%로 높게 나왔습니다.
지금은 `exclude_receivers` 설정과 "인자에 함수가 있으면 핸들러 등록으로
판정한다"는 구조적 규칙으로 걸러 냅니다.

**둘째, 정적으로 결정할 수 없는 경로가 있습니다.**
`` `/users${isRegister ? '' : '/login'}` ``에서는 치환이 경로 세그먼트 전체를
차지하지 않으므로 어떤 엔드포인트인지 확정할 수 없습니다. 이런 경우를 연결
실패로 계산하면 지표가 왜곡되므로, `dynamic`으로 따로 집계하여 별도로
보고합니다.

## 6. 랭킹

팩에 무엇을 담을지 결정하는 계산식입니다.

```
score(n) = ( α·BM25(질의, n)
           + β·PPR(시드로부터)
           + γ·recency(n)
           + δ·cochange(n, 시드)
           + ε·centrality(n) ) × kind_prior(n)
```

### α: 어휘 일치도

SQLite의 FTS5를 사용하며, 컬럼마다 가중치를 다르게 줍니다.
이름 10, 분해된 토큰 6, 시그니처 3, 문서 2, 경로 0.5입니다.

경로 가중치를 낮게 잡은 데에는 이유가 있습니다. 초기에는 경로가 점수를
지배했고, 그 결과 `src/main/resources/db/migration/V013__delete-table-users-articles.sql`
같은 파일이 "댓글 삭제" 질의의 상위를 차지했습니다.

`tokens` 컬럼에는 식별자를 분해한 결과를 넣습니다. `deleteComment`를
`"delete Comment"`로도 색인하므로, 자연어 질의가 카멜케이스 식별자와 연결되는
경우를 대부분 해결합니다.

### β: 개인화 페이지랭크

질의가 지목한 시드에서 출발하여 그래프를 따라 퍼지는 확률입니다. 호출, 주입,
import, 동시 변경 엣지를 모두 무향으로 다룹니다. 어떤 함수를 호출하는 쪽도
호출당하는 쪽만큼 맥락으로서 중요하기 때문입니다.

감쇠 계수는 0.5로 정했습니다. 이 값을 높이면 연결이 많은 이웃이 시드보다
높은 점수를 받습니다.

| 감쇠 계수 | 시드 | 1홉 | 2홉 |
|---|---|---|---|
| 0.85 | 0.35 | 0.46 (역전이 일어납니다) | 0.20 |
| 0.50 | 0.58 | 0.33 | 0.08 |

질의가 직접 지목한 노드가 가장 높아야 하므로 재시작 확률을 크게 잡았습니다.

이 계산은 시드에 의존하므로 미리 계산해 둘 수 없습니다. 이것이 뒤에 설명하는
"전역 계산을 쓰기 경로에서 제외한다"는 설계의 근거가 됩니다.

### δ: 동시 변경 결합도

git 이력에서 늘 함께 바뀌어 온 파일에 점수를 줍니다. 호출도 import도 없지만
실제로는 결합되어 있는 관계를 찾아냅니다. 구조 그래프만으로는 볼 수 없는
정보입니다.

파일 25개를 넘게 바꾼 커밋은 신호에서 제외합니다. 대규모 리팩터링이나 서식
정리 커밋이 모든 파일을 서로 묶어 버리기 때문입니다. 가중치는 동반 횟수에
`ln(1+n)`을 적용하여 과대평가를 막습니다.

### γ: 최근성

파일이 마지막으로 수정된 시각을 기준으로 반감기 30일 지수 감쇠를 적용합니다.
오늘 고친 파일은 1.0, 30일 전은 0.5, 1년 전은 거의 0이 됩니다. 선형 감쇠는
오래된 코드를 과하게 낮추고, 계단 함수는 경계에서 값이 급변합니다.

### kind_prior: 파일은 답이 아닙니다

| 종류 | 사전 확률 |
|---|---|
| Symbol | 1.00 |
| Route | 0.85 |
| ApiCall | 0.70 |
| File | 0.30 |

파일은 심볼을 담는 단위일 뿐입니다. 에이전트가 원하는 것은 "이 파일 어딘가"가
아니라 "이 함수의 이 줄"입니다. 같은 파일에 속한 심볼이 이미 팩에 담겼으면
파일 노드는 아예 제외합니다.

### 관련성이 없으면 자격을 얻지 못합니다

중심성과 최근성은 이미 관련이 있다고 판단된 노드들 사이에서 순위를 가르는
신호이며, 관련성 자체를 뜻하지 않습니다. 이 구분을 두지 않았을 때
`save`, `getBySlug` 같은 연결이 많은 심볼이 어휘 일치도와 그래프 근접도가
모두 0인데도 중심성만으로 팩에 들어왔습니다. 벤치 결과에서 27개 항목 가운데
12개가 이런 경우였습니다.

지금은 어휘 일치가 있거나 그래프 근접도가 임계값을 넘어야 후보가 됩니다.

### 예산은 상한이며 목표가 아닙니다

점수가 최고 점수의 8%에 미치지 못하는 항목은 예산이 남아 있어도 담지 않습니다.
예산을 늘 끝까지 채우면 관련 코드가 적은 작업에서 오히려 손해가 발생합니다.
관련 파일이 3.4k 토큰뿐인 작업에 4k 예산을 모두 사용하여 절감량이 -15%로
측정된 사례가 있었습니다.

### 가중치는 설정 파일에 있습니다

α부터 ε까지의 값은 `nunchi.shared.toml`에 있으며, TUI의 팩 미리보기 화면에서
조정하면 즉시 다시 계산됩니다. 저장하면 그 시점부터 에이전트도 같은 값을
사용합니다. 랭킹 조정이 감각에 의존하는 작업에서 관찰에 근거하는 작업으로
바뀝니다.

## 7. 순회 엔진과 저장 엔진을 분리합니다

nunchi는 SQLite를 사용하며 그래프 데이터베이스를 쓰지 않습니다. 근거가 있습니다.

엣지 100만 개는 메모리에 약 50MB로 들어갑니다. 그래서 그래프를 통째로 올려
두고 개인화 페이지랭크와 중심성을 일반 코드로 계산합니다. 이 구조에서는
그래프 데이터베이스가 제공하는 순회 성능 이점이 대부분 상쇄됩니다.

반면 이 도구의 작업 특성은 임베디드 그래프 데이터베이스에 불리합니다.

| 작업 특성 | 성격 |
|---|---|
| 파일을 저장할 때마다 증분 인덱싱을 수행함 | 작고 잦은 쓰기이며 OLTP에 가까움 |
| 에이전트가 질의함 | 소규모 지점 조회를 저지연으로 여러 번 수행함 |

Kuzu의 후속 프로젝트인 LadybugDB 등은 컬럼 기반 저장을 사용하며 분석 작업을
지향한다고 스스로 밝히고 있습니다. 또한 임베디드 데이터베이스는 두 프로세스가
동시에 쓰기로 열 수 없는데, nunchi는 인덱서가 쓰기를 담당하고 MCP 서버가
읽기를 담당하는 별도 프로세스 구조입니다. SQLite는 WAL 모드에서 쓰기 도중에도
읽기가 가능합니다.

다만 이 결정은 되돌릴 수 있도록 만들었습니다. 저장 계층은 여섯 개 메서드
(`upsert_nodes`, `upsert_edges`, `neighbors`, `paths`, `search`, `rank`) 뒤에
있으므로 교체 비용이 하루를 넘지 않습니다.

## 8. 갱신 비용을 세 계층으로 나눕니다

코드가 바뀔 때마다 전체를 다시 만들지는 않습니다. 중요한 것은 어떤 계산을
쓰기 경로에 두는지 결정하는 일입니다.

| 계층 | 대상 | 파일 하나가 바뀔 때 | 처리 시점 |
|---|---|---|---|
| A. 파일 내부 | 심볼, 시그니처, 파일 안의 엣지 | 1ms 미만 | 즉시 |
| B. 파일 사이 엣지 | 이 파일을 참조하던 곳 | 역인덱스로 수십 개 | 즉시 |
| C. 전역 파생값 | 페이지랭크, 임베딩, 동시 변경 통계 | 전체를 훑어야 함 | 즉시 처리하지 않음 |

C 계층을 쓰기 경로에서 완전히 제외했습니다.

- 개인화 페이지랭크는 저장하지 않습니다. 시드에 의존하므로 미리 계산할 수 없고,
  질의 시점에 메모리에서 계산합니다.
- 동시 변경 통계는 git 이력에 기반하므로 커밋 시점에만 갱신합니다. 파일을
  저장하는 동작과는 무관합니다.

이 분리를 하지 않으면 파일을 저장할 때마다 수 초씩 멈춥니다.

## 9. 브랜치를 전환할 때 재파싱을 피합니다

인덱스는 워킹트리의 특정 상태를 반영한 결과물입니다. `git checkout`이 그
상태를 바꾸면 인덱스도 다시 만들어야 합니다. 그런데 실무에서 브랜치 전환은
왕복으로 일어납니다.

해법은 A 계층의 성질에서 나옵니다.

```
parse(blob_content) → { symbols, edges, spans }     브랜치와 무관합니다
```

그래서 브랜치가 아니라 파일 내용의 해시를 키로 캐싱합니다. git이 blob을
다루는 방식과 같습니다.

| 전환 | 캐시가 없을 때 | 캐시가 있을 때 |
|---|---|---|
| main에서 feature로 (처음) | 1,200개 파싱 | 1,200개 파싱하며 캐시를 채움 |
| feature에서 main으로 (복귀) | 1,200개 파싱 | 파싱 없음 |

실측에서 재인덱싱 시간이 0.65초에서 0.20초로 줄었고 캐시 적중률은 100%였습니다.

캐시 키는 git의 blob SHA가 아니라 워킹트리에 있는 파일 내용의 해시입니다.
`core.autocrlf`가 켜진 Windows에서는 워킹트리가 CRLF이고 blob이 LF이므로 두
값이 달라집니다. 실제로 파싱하는 대상은 워킹트리 내용이므로 그것을 해시합니다.

브랜치 전환이 실제로 강제하는 재계산은 B 계층 하나뿐입니다.

## 10. 오래된 인덱스를 다루는 방식

인덱스는 언젠가 실제 코드와 어긋나게 됩니다. 가장 흔한 원인은 에이전트 자신이 방금 코드를
고쳤기 때문입니다. 파일을 수정한 직후 워처가 반응하기 전에 다음 팩 요청이
들어오는 상황은 일상적으로 발생합니다.

그래서 팩을 조립할 때 파일을 검증합니다.

```
1. 수정 시각과 크기를 비교합니다        (비용이 낮으며 대부분 여기서 통과합니다)
2. 일치하지 않을 때만 해시를 계산합니다
3. 해시도 다르면 stale 목록에 넣고 본문 없이 반환합니다
4. 파일이 아예 없으면 역시 stale로 처리합니다
```

잘못된 좌표를 확신을 담아 제공하는 것보다 오래되었다고 알리는 편이 언제나 낫습니다.
`stale` 항목을 받은 에이전트는 그 부분만 직접 읽으면 됩니다.

인덱싱 쪽에서도 같은 원칙을 적용합니다. 인덱싱은 발견한 파일을 upsert하기
때문에, 삭제되거나 이동한 파일을 그대로 두면 인덱스에 영원히 남아 존재하지
않는 좌표를 반환합니다. 그래서 인덱싱을 마칠 때마다 이번에 발견되지 않은
파일의 노드와 끊어진 엣지를 제거합니다. 이어서 아무도 참조하지 않게 된
의존성, 커밋, 저자 노드도 정리합니다. 이 삭제는 연쇄적으로 일어나므로
변화가 없을 때까지 반복합니다. 커밋이 지워진 다음에야 그 저자가 고아가
되기 때문입니다. 다만 `Repo`와 `Solution`은 애초에 들어오는 엣지가 없는
루트 노드이므로 대상에서 제외합니다.

## 11. MCP 도구를 다섯 개로 제한합니다

MCP 도구의 스키마는 대화가 시작되는 시점부터 계속 비용을 발생시킵니다.
세션이 시작되기도 전에 수만 토큰이 도구 정의로 소모됩니다.

그래서 `nunchi_pack`, `nunchi_find`, `nunchi_neighbors`, `nunchi_impact`,
`nunchi_doctor` 다섯 개만 노출합니다. 여러 질의를 묶어야 할 때는 MCP 대신
CLI를 사용합니다. CLI에는 스키마 비용이 없고 Bash 한 번으로 여러 명령을
이어서 실행할 수 있습니다.

같은 이유로 TUI에도 고유 기능을 두지 않습니다. TUI는 CLI가 이미 제공하는
데이터를 보여 주는 화면일 뿐입니다. TUI에서만 할 수 있는 일이 생기면 자동화가
막히고 최초 적용이 수작업으로 변합니다.

## 12. 되돌리기 어려운 결정과 그 근거

바꾸려면 아래 근거를 먼저 반박해야 합니다.

| 결정 | 근거 | 뒤집어야 하는 조건 |
|---|---|---|
| SQLite를 쓰고 그래프 DB를 쓰지 않음 | 7절에 설명함 | 엣지가 5천만을 넘거나, 팀이 공유하는 서비스로 운영하거나, 4홉 이상 임의 경로 탐색이 상시 질의가 됨 |
| 감쇠 계수를 0.5로 둠 | 6절에 실측을 표로 제시함 | 순회를 유향으로 바꾸면 다시 측정해야 함 |
| 프레임워크 규칙을 데이터로 둠 | 업무 장비가 분리되어 재빌드와 재배포 비용이 큼 | 그 제약이 사라지면 재검토할 수 있음 |
| MCP 도구를 다섯 개로 제한함 | 11절에 설명함 | 일괄 실행은 CLI로 해결되므로 늘릴 이유가 없음 |
| TUI를 조회 전용으로 유지함 | 11절에 설명함 | 없음 |
| 벡터 임베딩을 넣지 않음 | 로컬 임베딩 모델이 필요하고, 업무 장비에 모델 파일을 배포하는 문제가 따로 있음 | 모델 배포 경로가 확보되면 추가할 수 있음 |

## 13. 현재의 한계

- **JPA 파생 쿼리 메서드를 해소하지 못합니다.** `findByStatus`처럼 소스에 본문이
  없는 메서드는 이름 규칙을 해석해야 합니다. `@Entity`와 `@Table`, MyBatis의
  어노테이션과 XML 매퍼, SQLAlchemy의 `__tablename__`은 지원하지만 파생 쿼리
  이름을 해석하는 기능은 아직 없습니다.
- **SCIP 정밀 경로를 연동하지 않았습니다.** 현재는 tree-sitter를 사용하는 빠른
  경로만 있으므로 파일 사이의 참조 해소가 이름에 기반한 추정입니다.
- **벡터 임베딩이 없습니다.** 식별자 분해와 설정에 기반한 동의어 사전으로
  대체했습니다.
- **동적으로 조립되는 API 경로를 볼 수 없습니다.** 정적 분석의 원리적 한계입니다.
- **호출에 기반한 라우팅을 지원하지 않습니다.** 현재 규칙 모델은 어노테이션과
  데코레이터만 다룹니다. Django의 `path("orders/", views.list)`나 Express의
  `app.get(path, handler)` 형태를 지원하려면 규칙 축을 하나 더 늘려야 합니다.
- **파일 단위 증분 갱신을 구현하지 않았습니다.** 워처는 전체를 다시 인덱싱합니다.
  내용 해시 기반 캐시 덕분에 비용은 낮습니다.
- **`nunchi bench`의 ungrounded 값은 대리 지표입니다.** 실제 에이전트 세션이
  아니므로 절대 절감률로 인용하면 안 됩니다.
