# 원리 — nunchi는 어떻게 토큰을 줄이는가

## 문제

에이전트가 코드베이스에서 무언가를 고치려면 먼저 구조를 알아야 합니다.
지금 방식은 **매번 처음부터 다시 알아내는 것**입니다.

```
1. Grep "retry"                    → 40 hits
2. Read OrderService.java …        → 18k tokens
3. Grep "payment"                  → 60 hits
4. Read 4 files                    → 22k tokens
   ⋮
   12 turns · 입력 ~60k tokens · 프런트 영향은 끝내 모름
```

같은 코드베이스에서 매 세션 이 일이 반복됩니다. 구조는 변하지 않았는데
매번 다시 발견합니다.

## 해법의 형태

구조를 **미리 계산해 두고**, 에이전트에게는 **답이 아니라 좌표**를 줍니다.

```
1. nunchi_pack{task:"주문 재시도 로직 수정", budget:4000}   → 3.8k tokens
2. Read OrderService.java:88-141   (팩이 지목한 범위만)     → 3k tokens
3. Edit
   3 turns · 입력 ~9k tokens · 프런트 훅 영향까지 인지
```

이 문서는 그 사이에서 무슨 일이 일어나는지 설명합니다.

---

## 1. 핵심 원칙: 답이 아니라 좌표

`nunchi_pack`이 돌려주는 것은 코드 덩어리가 아니라 **랭킹된 좌표 목록**입니다.

```jsonc
"items": [
  { "tier": "L2", "ref": "api/.../OrderService.java:88-141",
    "sym": "findOne", "body": "..." },              // 전체 본문 — 상위 2~3개만
  { "tier": "L1", "ref": "api/.../OrderController.java:44",
    "sym": "getOrder",
    "sig": "@GetMapping(\"/api/orders/{id}\") ..." }, // 시그니처 + 문서
  { "tier": "L0", "ref": "api/.../OrderServiceTest.java:12",
    "sym": "findOne_retriesOnTimeout" }             // 좌표 한 줄
]
```

에이전트는 이 목록을 보고 **실제로 필요한 범위만** Read합니다.
"파일 12개 전체(≈35k)" 대신 "심볼 40개(≈4k) + 정확한 위치"입니다.

절감의 실체는 두 동작입니다:

- **선별** — 수천 개 노드에서 관련된 수십 개만 고른다
- **강등** — 예산이 모자라면 L2 → L1 → L0로 상세도를 낮춘다

## 2. 그래프에는 무엇이 들어 있나

노드 18종, 엣지 19종입니다. 중요한 것만 추리면:

```
Repo ──contains──▶ File ──contains──▶ Symbol
                                        │
                    ┌───────────────────┼──────────────────┐
                    ▼                   ▼                  ▼
                  calls              injects            defined_in
              (다른 Symbol)        (Spring DI)          (File)

Route ──handles──▶ Symbol          ApiCall ──calls_api──▶ Route
(@GetMapping)      (컨트롤러 메서드)   (fetch/axios)

File ──co_changed_with──▶ File     File ──modified_by──▶ Commit
(git 이력에서 함께 바뀐 파일)
```

각 엣지는 **provenance**(`fast` / `precise`)와 **confidence**를 가집니다.
tree-sitter 휴리스틱으로 만든 엣지와 빌드 기반 정밀 해소를 구분하기 위해서입니다.

## 3. 왜 프레임워크 의미론이 따로 필요한가

Spring에서는 **호출 관계가 소스에 구문적으로 존재하지 않습니다.**

| 실제 관계 | 소스에 보이는 것 |
|---|---|
| `GET /api/orders` → 컨트롤러 메서드 | `@GetMapping` 어노테이션뿐 |
| 서비스 → 구현체 | `@Autowired` + **인터페이스** |
| `findByStatus(...)` | **메서드 본문이 아예 없음** (JPA 파생 쿼리) |

tree-sitter로 콜그래프만 뽑으면 호출 엣지가 거의 생기지 않아
**그래프가 사실상 파일 목록으로 전락합니다.**

실측이 이를 확인해줍니다. RealWorld(Spring Boot) 인덱싱 시 미해소 호출 상위는
`save`(45회 — JPA 리포지터리, 본문 없음), `build`/`builder`(85회 — Lombok 생성 코드)였습니다.

그래서 어노테이션을 1급으로 다룹니다:

- `@GetMapping("/{slug}")` + 클래스의 `@RequestMapping("/api/articles")`
  → `Route(GET, /api/articles/{})` 노드 + `HANDLES` 엣지
- `@Service` + `final` 필드(Lombok `@RequiredArgsConstructor`) → `INJECTS` 엣지
- `fetch(\`/api/articles/${slug}\`)` → `ApiCall` 노드

### 이 규칙은 데이터입니다

`@GetMapping`을 Rust 코드에 박아두면 새 프레임워크나 사내 관용구마다
재빌드·재배포가 필요합니다. 프레임워크 의미론은 몇 가지 정형으로 환원되므로
규칙 테이블로 뺐습니다:

```toml
[[framework.route]]      # 메서드 어노테이션 → 라우트
[[framework.base_path]]  # 클래스 어노테이션 → 경로 접두
[[framework.bean]]       # 클래스 어노테이션 → DI 등록
[[framework.inject]]     # 필드 어노테이션 → 주입
[[framework.http_client]] # n번째 문자열 인자가 URL
```

Spring · NestJS · Micronaut · ASP.NET · Ktor가 모두 이 틀에 들어갑니다.

## 4. 교차 저장소 — grep으로는 원리적으로 불가능한 것

```
  React                          Spring Boot                     DB
  ─────                          ───────────                     ──
  useOrder.ts:31                 OrderController.java:44
  fetch(`/api/orders/${id}`) ──▶ @GetMapping("/api/orders/{id}")
        │        CALLS_API              │ HANDLES
        │                               ▼
        │                        OrderService.findOne
        │                               │ INJECTS
        │                               ▼
        │                        OrderRepository ──persists_to──▶ orders
```

연결은 **경로 템플릿 정규화**로 이뤄집니다:

| 표기 | 출처 | 정규화 |
|---|---|---|
| `/api/orders/{id}` | Spring | `/api/orders/{}` |
| `/api/orders/:id` | Express, react-router | `/api/orders/{}` |
| `` `/api/orders/${id}` `` | JS 템플릿 | `/api/orders/{}` |

세 표기가 같은 문자열이 되므로 매칭은 단순 비교로 끝납니다.

*"주문 조회 API 응답 필드를 바꾸면 뭐가 깨지나"* 에 프런트 훅·컴포넌트,
백엔드 서비스, 테이블까지 한 번에 답할 수 있는 이유입니다.

### 정직해야 할 두 지점

**① 라우트 정의는 호출이 아니다.** `this.post('/users', handler)`(miragejs),
`app.get('/x', h)`(Express)는 서버 라우트 등록이지 클라이언트 호출이 아닙니다.
초기 구현에서 이 오탐이 탐지 21건 중 16건이었고, 같은 API 명세를 미러링하니
백엔드와 잘 매칭돼 **지표가 95%로 좋아 보였습니다.**
지금은 `exclude_receivers`와 "인자에 함수가 있으면 핸들러 등록"이라는
구조적 판정으로 걸러냅니다.

**② 정적으로 알 수 없는 경로가 있다.**
`` `/users${isRegister ? '' : '/login'}` `` 은 치환이 세그먼트 전체가 아니어서
어떤 엔드포인트인지 결정할 수 없습니다. 연결 실패로 세면 지표가 왜곡되므로
`dynamic`으로 따로 집계하고 별도 보고합니다.

## 5. 랭킹 — 무엇을 팩에 넣을지

```
score(n) = ( α·BM25(질의, n)
           + β·PPR(시드로부터)
           + γ·recency(n)
           + δ·cochange(n, 시드)
           + ε·centrality(n) ) × kind_prior(n)
```

### α — BM25

SQLite FTS5. 컬럼별 가중치가 있습니다: **name 10 · tokens 6 · signature 3 · doc 2 · path 0.5**.

경로 가중치를 낮게 잡은 데는 이유가 있습니다. 초기에는 경로가 BM25를 지배해서
`src/main/resources/db/migration/V013__delete-table-users-articles.sql` 같은 파일이
"댓글 삭제" 질의의 상위를 점령했습니다.

`tokens` 컬럼은 **분해된 식별자**입니다. `deleteComment` → `"delete Comment"`.
자연어 질의가 카멜케이스 식별자에 닿는 대부분의 경우가 이걸로 해결됩니다.

### β — Personalized PageRank

질의가 짚은 시드에서 출발해 그래프를 따라 퍼지는 확률입니다.
호출·주입·import·동시변경 엣지를 **무향으로** 다룹니다 — "이 함수를 호출하는 쪽"도
"호출당하는 쪽"만큼 컨텍스트로 중요하기 때문입니다.

**damping은 0.5입니다.** 값이 높으면 차수가 큰 이웃이 시드를 추월합니다:

| damping | 시드 | 1홉 | 2홉 |
|---|---|---|---|
| 0.85 | 0.35 | **0.46** ← 역전 | 0.20 |
| 0.50 | **0.58** | 0.33 | 0.08 |

질의가 직접 짚은 노드가 가장 높아야 하므로 재시작 확률을 크게 잡았습니다.

PPR은 **시드에 의존하므로 미리 계산할 수 없습니다.** 이것이 뒤에 나올
"쓰기 경로에서 전역 계산을 뺀다"는 설계의 근거입니다.

### δ — 동시변경 결합도

git 이력에서 **늘 함께 바뀌어온 파일**입니다. 호출도 import도 없지만 실제로
결합된 관계를 잡습니다. 구조 그래프가 볼 수 없는 정보입니다.

파일 25개를 넘는 커밋은 신호에서 제외합니다 — 대규모 리팩터링이나 포맷팅 커밋이
모든 파일을 서로 묶어버리기 때문입니다. 가중치는 동반 횟수의 `ln(1+n)`으로 눌러
과대평가를 막습니다.

### kind_prior — 파일은 답이 아니다

| 종류 | 사전확률 |
|---|---|
| Symbol | 1.00 |
| Route | 0.85 |
| ApiCall | 0.70 |
| File | 0.30 |

파일은 **컨테이너**입니다. 에이전트가 원하는 것은 "이 파일 어딘가"가 아니라
"이 함수의 이 줄"입니다. 같은 파일의 심볼이 이미 팩에 담겼으면 파일 노드는
아예 제외합니다.

### 가중치는 설정입니다

α~ε는 `nunchi.toml`에 있고, TUI 팩 미리보기에서 슬라이더로 조정하면 **즉시
재랭킹**됩니다. `s`로 저장하면 그 순간부터 에이전트도 같은 값을 씁니다.
랭킹 튜닝이 감이 아니라 관찰이 됩니다.

## 6. 순회 엔진은 저장 엔진이 아니다

`nunchi`는 SQLite를 씁니다. 그래프 DB가 아닙니다. 이유가 있습니다.

엣지 100만 개는 메모리에 **약 50MB**로 들어갑니다. 그래서 그래프를 통째로 올려
PPR과 중심성을 일반 코드로 계산합니다. 이 구조에서는 그래프 DB의 순회 이점이
대부분 상쇄됩니다.

반면 우리 워크로드는 임베디드 그래프 DB에 불리합니다:

| 우리 패턴 | 성격 |
|---|---|
| 파일 저장 시 증분 재인덱싱 | **작고 잦은 쓰기** (OLTP형) |
| 에이전트 질의 | 소규모 포인트 질의, **저지연 다수** |

LadybugDB 같은 Kuzu 후계들은 컬럼나 기반 **분석 워크로드** 지향이라고 스스로
밝힙니다. 그리고 임베디드 DB는 두 프로세스가 동시에 쓰기로 열 수 없는데,
우리는 인덱서(쓰기)와 MCP 서버(읽기)가 별도 프로세스입니다.
SQLite는 **WAL 모드로 쓰기 중 동시 읽기가 기본 보장**됩니다.

다만 이 결정은 되돌릴 수 있게 두었습니다. 저장 계층은 6개 메서드
(`upsert_nodes` / `upsert_edges` / `neighbors` / `paths` / `search` / `rank`)
뒤에 있어서 교체 비용이 하루 이내입니다.

## 7. 갱신 비용의 3계층

코드가 바뀔 때마다 전체를 다시 만들지 않습니다. 중요한 것은 **무엇을 쓰기 경로에
두느냐**입니다.

| 계층 | 대상 | 파일 1개 변경 시 | 시점 |
|---|---|---|---|
| **A. 파일 내부** | 심볼, 시그니처, 파일 내 엣지 | **<1ms** | 즉시 |
| **B. 파일 간 엣지** | 이 파일을 참조하던 곳 | 역인덱스로 수십 개 | 즉시 |
| **C. 전역 파생값** | PageRank, 임베딩, 동시변경 통계 | **전체 스캔** | **절대 즉시 아님** |

C를 쓰기 경로에서 완전히 뺐습니다:

- **PPR** → 애초에 저장하지 않습니다. 시드 의존적이라 미리 계산이 불가능하고,
  질의 시점에 메모리에서 돕니다
- **동시변경 통계** → git 이력 기반이므로 **커밋 시점에만** 갱신합니다.
  파일 저장과 무관합니다

이 분리를 안 하면 파일을 저장할 때마다 수 초씩 멈춥니다.

## 8. 브랜치 전환 — 내용의 함수라는 통찰

인덱스는 워킹트리 한 상태의 투영입니다. `git checkout`이 그 상태를 갈아치우면
인덱스도 갈아엎힙니다. 그리고 실무에서 이건 왕복입니다.

해법은 A 계층의 성질에서 나옵니다:

```
parse(blob_content) → { symbols, edges, spans }     ← 브랜치와 무관
```

**브랜치가 아니라 내용 해시로 캐싱합니다.** git이 blob을 다루는 방식 그대로입니다.

| 전환 | 캐시 없음 | 캐시 있음 |
|---|---|---|
| main → feature (최초) | 1,200 파싱 | 1,200 파싱 (캐시 채움) |
| feature → main (복귀) | 1,200 파싱 | **파싱 0회** |

실측으로 재인덱싱이 0.65s → 0.20s, 캐시 적중률 100%가 됩니다.

캐시 키는 **git blob SHA가 아니라 워킹트리 파일 내용 해시**입니다.
`core.autocrlf=true`인 Windows에서는 워킹트리가 CRLF, blob이 LF라 두 값이 갈리기
때문입니다. 우리가 실제로 파싱하는 것은 워킹트리 내용이므로 그것을 해시합니다.

checkout이 실제로 강제하는 재계산은 **B 계층 하나**뿐입니다.

## 9. 낡은 인덱스보다 나쁜 것은 없다

인덱스는 **반드시 낡습니다.** 무엇보다 **에이전트 자신이 방금 코드를 고쳤기**
때문입니다. Edit 직후 워처가 반응하기 전에 다음 `pack`이 들어오는 레이스는 일상입니다.

그래서 팩을 조립할 때 파일을 검증합니다:

```
1. mtime + size 비교        ← 싸다. 대부분 여기서 통과
2. 불일치 시에만 해시 계산
3. 해시도 불일치 → stale 목록에 넣고 본문 없이 반환
4. 파일이 아예 없음  → 역시 stale. 없는 좌표를 주면 안 된다
```

인덱싱 쪽에서도 대칭으로 처리합니다. 인덱싱은 발견한 파일을 upsert만 하므로,
삭제·이동된 파일을 그대로 두면 인덱스에 영원히 남아 존재하지 않는 좌표를 반환하게
됩니다. 그래서 매 인덱싱 끝에 **이번에 발견되지 않은 파일의 노드와 끊긴 엣지를
제거**합니다. 워처를 띄워두면 이 누적이 계속 쌓이므로 특히 중요합니다.

**틀린 좌표를 자신 있게 주는 것보다 낡았다고 말하는 편이 항상 낫습니다.**
`stale` 필드를 받은 에이전트는 그 항목만 직접 Read하면 됩니다.

## 10. 왜 툴이 5개뿐인가

MCP 툴 스키마는 **대화 시작 시점부터 상시 비용**입니다. 세션 시작 전에 이미
수만 토큰이 도구 정의로 소모됩니다.

그래서 `nunchi_pack` / `find` / `neighbors` / `impact` / `doctor` 다섯 개만
노출합니다. 여러 질의를 묶어야 하면 MCP 대신 **CLI**를 씁니다 — 스키마 토큰이
0이고 Bash 한 번으로 배칭됩니다.

같은 이유로 TUI도 고유 기능을 갖지 않습니다. TUI는 CLI가 이미 내놓는 데이터의
뷰어일 뿐입니다. TUI에서만 되는 일이 생기는 순간 자동화가 막히고 온보딩이
수작업이 됩니다.

---

## 한계

정직하게 적어둡니다.

- **JPA 리포지터리 메서드는 해소되지 않습니다.** `save`, `findByStatus`는 소스에
  본문이 없습니다. `PERSISTS_TO` 엣지(Entity/Table 계층)가 아직 없습니다.
- **SCIP 정밀 경로가 없습니다.** 현재는 tree-sitter 빠른 경로만이라 크로스파일
  참조 해소가 이름 기반 휴리스틱입니다. `scip-java`/`scip-typescript` 연동이
  다음 단계입니다.
- **벡터 임베딩이 없습니다.** 로컬 임베딩 모델이 필요합니다. 대신 식별자 분해와
  설정 기반 동의어로 대체했습니다.
- **동적으로 조립되는 API 경로는 볼 수 없습니다.** 정적 분석의 원리적 한계입니다.
- **워처는 전체 재인덱싱을 돕니다.** 콘텐츠 주소 캐시 덕분에 비용은 낮지만
  파일 단위 부분 갱신은 아직입니다.
- **외부 의존성 노드는 정리되지 않습니다.** 마지막 참조가 사라져도 `ExternalDep`
  노드는 남습니다. 랭킹에 영향은 미미하지만 완전하지 않습니다.
